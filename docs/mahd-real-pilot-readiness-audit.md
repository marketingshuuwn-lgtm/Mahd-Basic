# تدقيق جاهزية Pilot حقيقي لعميل واحد داخل مَهَد

## الحكم المختصر

**مَهَد غير جاهزة بعد لتشغيل Pilot منتجي حقيقي لعميل واحد مع قياس موثوق للأخطاء والجهد والتسليم.** الجاهز حاليًا هو Pilot تقني محلي: نموذج كيانات، مستودع `localStorage`، صندوق مزامنة، حارس موافقة، موصل Trello، و31 اختبارًا ناجحًا مع بناء إنتاج ناجح.

الفرق مهم. Pilot المنتج يحتاج أن يعمل شخص أو فريق فعلي داخل مَهَد على دورة عميل كاملة، وأن تسجل المنصة ما حدث أثناء الدورة: من أنشأ ماذا، كم استغرق، أين وقع الخطأ، ما الذي احتاج إعادة عمل، وما الذي سُلّم ومتى. هذه السلسلة غير موجودة كمسار واحد قابل للقياس بعد.

## معيار Pilot المعتمد للفحص

اعتبرت Pilot ناجحًا فقط إذا تحققت السلسلة التالية داخل مَهَد، دون الحاجة إلى Trello كواجهة تشغيل:

> عميل محفوظ → مشروع مرتبط → مهمة مرتبطة → مخرج مرتبط → إسناد ومراجعة → اعتماد وتسليم → سجل وقت وجهد وأخطاء ونتيجة.

كما اشترطت أن تكون المقاييس مرتبطة بكيانات مَهَد الجديدة، لا بمهام النظام الشخصي القديم أو بيانات Trello العامة فقط.

## فحص دورة العميل

| المرحلة | الموجود فعليًا | الحكم |
|---|---|---|
| إنشاء العميل | نموذج `createClient` ومسار إنشاء محلي، وحفظ في المستودع المحلي | موجود محليًا |
| إنشاء المشروع | `createProject` يفرض `clientId` ومسار إنشاء محلي | موجود محليًا |
| إنشاء المهمة | `createTask` يفرض مشروعًا وعميلًا، أو يسمح بمسار عمل داخلي | موجود محليًا |
| إنشاء المخرج | أضيف `createDeliverable` بعلاقة عميل ومشروع ومهمة اختيارية | موجود في النموذج والمستودع، ولم يثبت بعد كدورة واجهية مكتملة |
| العمل الداخلي | أضيف `createInternalWork` ككيان مستقل عن العميل والمشروع | موجود في النموذج والمستودع، لكنه ليس بعد دورة تشغيل مكتملة داخل صفحة العمل الداخلي |
| عرض العلاقات | صفحات العملاء والمشاريع والمهام تعرض كيانات محلية إلى جانب قراءة Trello | جزئي؛ لا يوجد عرض تفصيلي كامل للمخرج وعلاقته بالمهمة والتسليم |
| الإسناد | المهمة تحمل `assigneeId`، لكن لا توجد عضوية أو هوية فريق فعلية | غير مكتمل |
| المراجعة والاعتماد | صندوق المزامنة يملك اعتمادًا محليًا لعمليات Trello | ليس اعتماد مخرج وتسليم منتجيًا عامًا |
| التسليم | توجد حقول `dueDate` وحقول حالة للمخرج، لكن لا يوجد سجل تسليم أو رابط حزمة تسليم أو حدث تسليم | غير مكتمل |

## فحص القياس

| القياس المطلوب | ما وجدته | الحكم |
|---|---|---|
| الأخطاء | توجد أخطاء تقنية في الواجهة وعمليات Trello، لكن لا يوجد كيان أو سجل `pilot_error` مرتبط بعميل ومشروع ومهمة ومخرج | غير موجود كقياس Pilot |
| الجهد والوقت | النظام القديم يملك `TimeTrackingSync` و`KpiView` ويقيس `timeSpentSeconds` لمهام عامة؛ لا يرتبط بنموذج مَهَد الجديد | موجود في النظام القديم فقط |
| إعادة العمل | لا يوجد حقل أو حدث يقيس عدد مرات إعادة المهمة أو المخرج للمراجعة | غير موجود |
| التأخير | توجد `dueDate` وحالات عامة، لكن لا يوجد قياس SLA أو فرق بين الموعد والتسليم الفعلي | جزئي وغير كافٍ |
| جودة التسليم | لا يوجد سجل قبول العميل، أو checklist تسليم، أو حالة تسليم موثقة مع وقت ومالك | غير موجود |
| أثر المزامنة | سجل المزامنة يقيس حالة العملية الخارجية ونجاحها أو فشلها وتعارضها | موجود للمزامنة، وليس لقياس Pilot كامل |
| خفض الجهد بنسبة 90% | لا توجد baseline أو مقارنة قبل/بعد أو عينة تشغيل حقيقية | لا يمكن إثباته حاليًا |

## ما تثبته الاختبارات الحالية

تشغيل الاختبارات الحالية أعطى **31 اختبارًا ناجحًا دون فشل**، ونجح بناء الإنتاج. تغطي الاختبارات نموذج العميل والمشروع والمهمة والمخرج والعمل الداخلي، المستودع المحلي والاستعادة، الاستمرارية، المزامنة، الصلاحيات، الأدوار، والتعارضات.

هذه نتيجة جيدة لصحة الأساس المنطقي، لكنها لا تثبت Pilot تشغيليًا؛ فالاختبارات لا تمثل مستخدمين حقيقيين، ولا تسجل زمنًا فعليًا أو أخطاء تشغيلية أو مخرجات تم تسليمها.

## ما يمنع إعلان Pilot حقيقي الآن

أول مانع هو أن التخزين محلي للمتصفح وليس مساحة مشتركة لفريق الوكالة. ثاني مانع هو عدم وجود مصادقة وعضويات وهوية فعلية تربط الإسناد والقرارات بالأشخاص. ثالث مانع هو أن المخرج والعمل الداخلي أضيفا إلى النموذج والمستودع، لكن لم تُثبت دورة واجهة كاملة لهما من الإنشاء حتى العرض والتسليم.

المانع الرابع هو غياب سجل قياس Pilot: لا يوجد مكان موحد لتسجيل بداية العمل ونهايته، الأخطاء، إعادة العمل، الاعتمادات، التسليم، وقبول العميل. المانع الخامس هو أن مؤشرات KPI والوقت الحالية تخص بنية المهام الشخصية القديمة، ولا تصلح وحدها كدليل على أداء عميل داخل نموذج مَهَد المنتجّي.

## ما يمكن اعتباره Pilot حاليًا

يمكن اعتبار الحالة الحالية **Pilot تقنيًا داخليًا** يشمل إنشاء كيانات محلية، اختبار الاستعادة، اعتماد عملية مزامنة، تنفيذ تحديث بطاقة واحدة في Trello، قراءة خارجية، وإظهار تعارض وحله محليًا. لا يمكن اعتباره Pilot عميل أو وكالة لأن الدورة لم تشمل مخرجًا وتسليمًا وقياسًا واقعيًا.

## بوابة القبول المطلوبة قبل Pilot الحقيقي

| البوابة | معيار القبول |
|---|---|
| دورة الكيانات | عميل واحد مع مشروع ومهمة ومخرج وعمل داخلي محفوظين وعروضهم مترابطة داخل مَهَد |
| دورة التنفيذ | يستطيع مستخدم تسجيل الإسناد، بدء العمل، تغيير الحالة، وإرسال المخرج للمراجعة |
| دورة التسليم | يوجد اعتماد داخلي وسجل تسليم واضح ورابط أو حزمة مخرج ووقت تسليم |
| دورة القياس | تسجل المنصة وقت الجهد، الأخطاء، إعادة العمل، التأخير، وحالة التسليم |
| دورة الفريق | لكل إجراء حساس هوية وعضوية ودور وصلاحية قابلة للتحقق |
| دورة الاستمرارية | يعيد مستخدم فتح مَهَد ويرى نفس الكيانات والسجل دون فقد العلاقات |
| Pilot محدود | ينجز فريق فعلي دورة عميل واحدة كاملة، ثم تُراجع النتائج مقابل baseline قبل التوسع |

## القرار

لا ينبغي إعلان نجاح Pilot الحقيقي الآن. المرحلة الصحيحة التالية ليست توسيع Trello، بل بناء **سجل تشغيل Pilot** وربطه بالمخرج والتسليم والوقت والأخطاء، ثم تنفيذ دورة داخلية كاملة لعميل واحد باستخدام مَهَد وحدها. بعد ذلك يمكن استخدام Trello كطبقة خلفية والتحقق من المزامنة دون الخلط بين نجاح الموصل ونجاح المنتج.
