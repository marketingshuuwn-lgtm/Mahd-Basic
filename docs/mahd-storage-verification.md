# تقرير التحقق من طبقة التخزين القابلة للاستبدال

## الحكم التنفيذي

تم تنفيذ وفحص **عزل معماري ناجح** بين مستودع مَهَد وتنفيذ التخزين المحلي. أصبح `createMahdRepository` يقبل محولًا مستقلًا، ويستخدم `createLocalStorageAdapter` افتراضيًا، ويمكن تشغيله مع `createMemoryStorageAdapter` دون تغيير واجهة المجال أو الواجهة.

لكن لا ينبغي وصف الحالة بأنها تخزين مشترك فعلي. التنفيذ الحالي لا يزال `localStorage` لكل متصفح، ولا يوجد بعد محول بعيد أو مشاركة بين المستخدمين أو مصادقة أو تزامن متعدد الأطراف.

## المكونات التي تم فحصها

| المكوّن | ما تم التحقق منه | الحكم |
|---|---|---|
| عقد المحول | `load()` و`save(snapshot)` و`clear()` مع `kind` | ناجح كأساس قابل للاستبدال |
| محول local | قراءة وكتابة snapshot ومعالجة JSON التالف | ناجح كتنفيذ انتقالي |
| محول memory | حفظ واستعادة داخل الذاكرة للاختبارات | ناجح كتنفيذ بديل للاختبار |
| مستودع مَهَد | يقبل `adapter` اختياريًا ويحافظ على `upsert` والكيانات | ناجح |
| نموذج المجال | لا يستورد localStorage ولا يعرف مزود التخزين | ناجح |
| واجهة الوكالة | تستخدم المستودع، ولا تستدعي محول التخزين مباشرة | ناجح في المسار المفحوص |
| الاختبارات | تغطي المحول البديل وعقد التخزين والحفظ والاستعادة | ناجح |
| التوثيق | يوضح ما لم يُعتمد من قرارات مشتركة | ناجح |

## ما تم إثباته فعليًا

يمكن تبديل تنفيذ التخزين من local إلى memory عند إنشاء المستودع، وتبقى عمليات حفظ العميل والمشروع والمهمة والمخرج والعمل الداخلي وسجل المزامنة تعمل من خلال الواجهة نفسها. هذا يثبت أن مستودع المجال لم يعد مرتبطًا مباشرة بواجهة `localStorage`.

تستخدم الواجهة الحالية `createMahdRepository()` فقط، بينما يختار المستودع محول local افتراضيًا. لا توجد استدعاءات مباشرة لمحول التخزين من مكونات الواجهة؛ وهذا يحافظ على نقطة تبديل واحدة.

أعيد تشغيل مجموعة الاختبارات الحالية ونجحت **33 اختبارًا دون فشل**، ثم نجح `npm run build` و`git diff --check`. آخر commit قبل تقرير التحقق هو `4f8f6c7`.

## ما لم يُثبت لأنه غير موجود بعد

لا يوجد محول `shared` فعلي يتصل بخدمة أو API. لا توجد هوية مساحة عمل أو مستخدم، ولا عزل بين فرق أو عملاء، ولا مصادقة، ولا عضويات، ولا صلاحيات تخزين، ولا قراءة وكتابة غير متزامنة، ولا معالجة تعارض بين جهازين.

العقد الحالي متزامن ويعمل على snapshot كاملة. هذا مناسب للـPilot المحلي، لكنه ليس كافيًا تلقائيًا لتخزين مشترك؛ المحول البعيد سيحتاج غالبًا إلى واجهة async أو طبقة orchestration، وإصدار snapshot أو `ETag` أو revision، وسياسة retry وoffline، ومخطط migrations.

## نطاق localStorage المتبقي خارج المستودع

التطبيق يحتوي أيضًا على استخدامات localStorage مستقلة في إعدادات التنبيهات والمظهر وأيام العمل والملاحظات ومساحات العمل وواجهة المهام واتصال Trello. هذه ليست كلها بيانات المنتج الأساسية، لكنها تعني أن تحويل مستودع مَهَد وحده لا يحول كل حالة التطبيق إلى تخزين مشترك.

يجب تصنيف هذه الاستخدامات لاحقًا إلى: حالة واجهة محلية، إعدادات مستخدم، أو بيانات مساحة عمل يجب نقلها إلى التخزين المشترك. لا ينبغي نقلها عشوائيًا إلى نفس snapshot.

## التوافق والترحيل

حافظ `createMahdRepository` على معامل `storage` القديم، لذلك تبقى اختبارات التخزين الحالية متوافقة. الإضافة الجديدة هي معامل `adapter` الذي يسمح بالانتقال التدريجي.

لا توجد migrations schema فعلية بعد. تطبيع snapshot يعيد المجموعات المفقودة إلى قوائم فارغة، لكنه ليس نظام versioned migration كاملًا. قبل أي محول مشترك يجب اعتماد سياسة versioning وترحيل واضحة.

## بوابة اعتماد التخزين المشترك

لا ينتقل المشروع إلى محول مشترك قبل اعتماد القرارات التالية: هوية مساحة العمل والعضو، نموذج المصادقة، حدود الوصول، ملكية السجلات، concurrency control، شكل API، async/error contract، offline/retry، migrations، وقواعد الاحتفاظ والنسخ الاحتياطي.

## النتيجة

بوابة **العزل القابل للاستبدال** ناجحة. بوابة **التخزين المشترك متعدد المستخدمين** لم تبدأ بعد، وهذا مقصود لأن القرار المعماري النهائي لم يعتمد. الخطوة التالية الصحيحة هي اعتماد مواصفات التخزين المشترك أولًا، ثم بناء محول بعيد يلتزم بالعقد أو ترقية العقد إلى async قبل توصيله بالواجهة.
