# عقد نسخة Trello-first

## الهدف

تعمل هذه النسخة من مَهَد كواجهة إنتاجية عربية فوق Trello للمهام فقط. لا تعتمد على مشروع Supabase الحالي، ولا تدّعي دعم فرق مَهَد أو صلاحيات مَهَد أو KPIs أو أتمتة أو Web Push في هذه المرحلة.

## مصدر الحقيقة

Trello هو مصدر الحقيقة المؤقت للبيانات التي تمثل المهمة. تستخدم الواجهة طبقة بيانات مستقلة بدل استدعاء Trello من المكوّنات. والكيانات التي لا يملكها Trello لا تُخزَّن داخله كحل دائم.

| مفهوم مَهَد | تمثيله في Trello خلال النسخة الأولى |
|---|---|
| مهمة | Card |
| مساحة عمل مَهَد | Board مختار من Trello |
| مرحلة التنفيذ | List mapping قابل للتهيئة |
| عنوان وملاحظات | Card name وdescription |
| موعد | Card due |
| إسناد | Card members |
| مهام فرعية | Checklist items |
| أرشفة | Card closed |
| روابط ومرفقات | Card attachments |

تظل مصفوفة أيزنهاور وتفاصيلها واجهة مَهَد مشتقة. ولا يُفترض أن تكون خصائص دائمة محفوظة في Trello في هذه المرحلة ما لم يكن لها mapping صريح ومعتمد.

## عقد مزود المهام

كل مزود يجب أن يعرض نفس قدرات القراءة والعمليات الأساسية، ويعيد نموذج مهمة مَهَد موحدًا:

```text
listTasks(connection, scope) -> Task[]
createTask(connection, input) -> Task
updateTask(connection, task, patch) -> Task
setTaskCompletion(connection, task, completed) -> Task
archiveTask(connection, task) -> void
listBoards(connection) -> Board[]
```

لا تستدعي المكونات `fetch` أو تفاصيل Trello. الواجهة تستمر في الاعتماد على `useTasks`، بينما يتغير التنفيذ خلفه فقط. يسمح ذلك بإضافة مزود Supabase مستقبلاً دون إعادة كتابة Matrix أو Timeline أو Planner أو Gantt.

## حدود الكتابة الأولى

العمليات التي ستكتب إلى Trello هي إنشاء البطاقة، تعديل العنوان والوصف والموعد، إغلاق/إعادة فتح البطاقة، وتحريكها بين Lists التي تمثل المراحل. لا تنفذ النسخة الأولى مزامنة ثنائية لخصائص مَهَد غير الممثلة في Trello، ولا تستخدم card description لتخزين قواعد أتمتة أو KPIs أو صلاحيات أو بيانات سرية.

## الأمان والقيود

تحتاج Trello API إلى token مفوض من المستخدم، وهو سر يمنح صلاحيات بحسب نطاق التفويض. لا يُضمّن أي token في الكود أو Git. في النسخة المبدئية يبقى token محليًا في متصفح المستخدم لأن النظام لا يملك backend بعد؛ هذا مقبول فقط لتجربة فردية محدودة وليس كحل فريق أو إنتاج. عند إدخال Supabase الجديد، ينتقل التفويض والتخزين إلى طبقة خادمية آمنة.

## مسار الانتقال لاحقًا

عند إضافة Supabase جديد، يظل `useTasks` متصلًا بعقد المزود نفسه. تضاف `workspace_id`, `project_id`, `created_by`, وsync metadata إلى مزود Supabase، بينما يحتفظ Trello بمراجع board/list/card الخارجية. يصبح Supabase مالك بيانات مَهَد، وتتحول Trello من مصدر حقيقة مؤقت إلى تكامل متزامن.
