# نطاق الإصدار الأول لمنصة مَهَد

## 1. القرار المعماري

تُبنى مَهَد كمنصة وكالة متعددة المستخدمين، لا كواجهة محلية فوق Trello. يعتمد الإصدار الأول على **Backend مستقل وقاعدة بيانات مشتركة** دون استخدام Supabase، مع الإبقاء على Trello طبقة بيانات انتقالية خلفية خلال فترة الانتقال.

يجب أن تكون المصادقة والعضويات والصلاحيات والتخزين المشترك خادمية. لا تُعتبر `localStorage` مصادقة أو عضوية أو حماية بيانات؛ ويُستخدم محليًا فقط كآلية انتقال أو cache غير موثوق، لا كمصدر حقيقة مشترك.

## 2. هدف الإصدار الأول

الهدف هو تمكين فريق وكالة تسويقية من العمل اليومي داخل مَهَد على مساحة عمل مشتركة، مع رؤية مختلفة للمالك والموظف، وحفظ مركزي للكيانات والعلاقات، وتسجيل عمليات المزامنة دون جعل الفريق يغادر مَهَد.

لا يهدف الإصدار الأول إلى استنساخ Notion أو Airtable بالكامل. يركز على مسار عملي واضح:

> مساحة العمل → العميل → المشروع → المهمة → المخرج، مع مسار مستقل للعمل الداخلي.

## 3. المستخدمون ومساحة العمل

يمثل النظام المستخدم كهوية مستقلة، وترتبط الهوية بعضوية في مساحة عمل واحدة أو أكثر. كل سجل تشغيلي يجب أن يرتبط بمساحة عمل، ولا يجوز الوصول إليه من خلال معرفه وحده دون التحقق من عضوية المستخدم في المساحة.

| الكيان | المسؤولية الأساسية |
|---|---|
| User | هوية الشخص وبيانات دخوله الأساسية |
| Workspace | حاوية بيانات الوكالة وعزلها |
| Membership | علاقة المستخدم بالمساحة وحالتها ودوره |
| Invitation | دعوة مستخدم للانضمام إلى مساحة |
| Role | الدور التشغيلي المعروف في الوكالة |
| Permission | الإجراء المسموح به على مورد محدد |

الإصدار الأول يدعم مساحة العمل المشتركة لفريق الوكالة. لا يُبنى تعدد المؤسسات المعقد أو نظام فوترة أو سوق إضافات ضمن هذا النطاق.

## 4. الأدوار التشغيلية

يحتفظ النظام بقاموس الأدوار التسعة المعتمد:

| المجموعة | الأدوار |
|---|---|
| القيادة | المالك |
| العميل | مدير الحساب |
| الإنتاج | كاتب محتوى، مصمم، مصور |
| التوزيع | مسؤول ميديا، منفذ حملات |
| العمليات | منسق مشاريع، مدير مشاريع |

تعريف الدور لا يمنح صلاحية تلقائيًا. تُخزن العضوية مع دورها، وتُقيّم الصلاحية في الخادم وفق مصفوفة مستقلة. في أول مرحلة تنفيذية، يبقى المالك قادرًا على إدارة مساحة العمل وتنفيذ عمليات المزامنة، بينما تُفعل صلاحيات الأدوار الأخرى تدريجيًا بعد اعتمادها واختبارها.

## 5. كيانات مَهَد الأساسية

| الكيان | العلاقة المطلوبة |
|---|---|
| Client | ينتمي إلى Workspace |
| Project | ينتمي إلى Workspace ويرتبط بعميل |
| Task | ينتمي إلى Workspace ويرتبط بمشروع وعميل، ويمكن إسناده لعضو |
| Deliverable | ينتمي إلى Workspace ويرتبط بمشروع وعميل، ويمكن ربطه بمهمة |
| InternalWork | ينتمي إلى Workspace ولا يرتبط بعميل أو مشروع خارجي |
| SyncOperation | ينتمي إلى Workspace ويرتبط بكيان محلي وهدف خارجي إن وجد |
| PilotRun | ينتمي إلى Workspace ويرتبط بعميل ومشروع ومخرج |
| PilotEvent | يرتبط بـ PilotRun ويسجل حدثًا ووقتًا وجهدًا |

تظل العلاقة الأساسية واضحة وغير قابلة للتخمين: **العميل ← المشروع ← المهمة ← المخرج**. العمل الداخلي مسار مستقل، ولا يُجبر على الارتباط بعميل أو مشروع.

## 6. تجربة المالك والموظف

يرى المالك مساحة العمل كاملة بحسب الصلاحيات المعتمدة، ويدير الأعضاء والدعوات وإعدادات المساحة وصندوق المزامنة. يرى الموظف ما تسمح به عضويته وإسناداته، مثل المهام والمشاريع والمخرجات التي يعمل عليها، ولا يحصل على صلاحيات المالك بمجرد تسجيل دخوله.

إخفاء عنصر من الواجهة ليس حماية. كل قراءة أو إنشاء أو تعديل أو اعتماد أو تنفيذ يجب أن يمر عبر تحقق خادمي من الجلسة والعضوية والدور والصلاحية وانتماء السجل إلى مساحة العمل.

## 7. المصادقة والعضويات

يشمل الإصدار الأول تسجيل الدخول والخروج، إنشاء الجلسة واستعادتها، حماية API، إنشاء مساحة العمل الأولى، دعوة عضو، قبول الدعوة، تعطيل العضوية، وتغيير الدور من خلال مستخدم مخول. لا تُحسم آلية مزود الهوية في هذه الوثيقة؛ تُحسم أثناء تصميم Backend مع الحفاظ على عدم استخدام Supabase.

يجب أن تكون الجلسة غير قابلة للتزوير من الواجهة، وأن تُرفض الطلبات التي لا تحمل هوية صالحة أو عضوية نشطة في مساحة العمل المطلوبة.

## 8. الصلاحيات في الإصدار الأول

تُنفذ الصلاحيات على الخادم، وتُعرّف لكل إجراء. الحد الأدنى للإجراءات هو: قراءة مساحة العمل، إدارة الأعضاء، إنشاء وتعديل العملاء والمشاريع والمهام والمخرجات والعمل الداخلي، إسناد المهمة، إرسال المخرج للمراجعة، اعتماد التسليم، مراجعة تعارض، اعتماد عملية مزامنة، وتنفيذ عملية مزامنة.

لا تُفعّل صلاحيات الأدوار الأخرى افتراضيًا. كل صلاحية غير معتمدة تبقى `not_decided` أو مرفوضة، ولا تتحول إلى سماح بسبب غياب تعريفها.

## 9. Pilot الحقيقي

يُشغل Pilot على عميل واحد فقط، والنطاق المرجعي الحالي هو **مستر آرت — مشروع التأسيس — مخرج استراتيجية العلامة**. يجب تسجيل دورة تشغيل فعلية داخل مَهَد، تشمل بدء العمل، دقائق جهد فعلية، تقدمًا، الأخطاء، إعادة العمل، المراجعة، التسليم، وقبول التسليم.

لا تُستخدم بيانات الاختبارات البرمجية كبيانات Pilot. لا يُعلن نجاح Pilot إلا عند وجود سجل مكتمل في التخزين المشترك، وبيانات قابلة للمراجعة، ونتيجة تسليم وقبول واضحة.

## 10. Trello في الإصدار الأول

يبقى Trello طبقة انتقالية ولا يصبح واجهة العمل اليومية. لا تُوسع المزامنة إلا بعد اجتياز Pilot الحقيقي وبوابة القبول.

يبدأ التوسع الأول بالمهام المرتبطة فقط:

| العملية | النطاق |
|---|---|
| إنشاء مهمة كبطاقة | مسموح بعد المعاينة والموافقة واجتياز بوابة Pilot |
| تحديث بطاقة مهمة مرتبطة | مسموح مع `externalId` ومراجعة |
| قراءة بطاقة مهمة | مسموحة وتحول الاختلاف إلى تعارض |
| إنشاء عميل أو مشروع | مؤجل حتى خريطة صريحة |
| مزامنة المخرج والعمل الداخلي | مؤجلة حتى اعتماد تمثيلهما |

كل كتابة تحتاج معاينة وموافقة وهوية معتمدة وتدقيقًا. لا تُطبق تغييرات Trello الواردة تلقائيًا على مَهَد.

## 11. خارج النطاق

لا يشمل الإصدار الأول تطبيقًا جوالًا، أو فوترة، أو نظامًا عامًا للقوالب، أو تعاونًا لحظيًا، أو محرر Blocks كاملًا، أو محرك Automations واسعًا، أو ذكاء اصطناعيًا تشغيليًا، أو مزامنة كاملة لكل كيانات Trello، أو نظام صلاحيات نهائيًا لكل الأدوار قبل اعتمادها.

## 12. بوابات القبول

| البوابة | معيار النجاح |
|---|---|
| Backend | API وقاعدة مشتركة واختبارات عزل Workspace |
| المصادقة | جلسة صالحة مطلوبة لكل API محمي |
| العضوية | مستخدمان يريان المساحة نفسها، ولا يصلان لمساحة أخرى |
| الصلاحيات | الخادم يرفض إجراءً غير مصرح حتى مع تعديل الواجهة |
| الكيانات | حفظ واستعادة العلاقات من جهازين مختلفين |
| Pilot | دورة فعلية مكتملة بجهد وأخطاء وتسليم وقبول |
| Trello | توسع محدود بعد البوابات السابقة وبنفس مسار المعاينة والموافقة |

## 13. القرار التالي

بعد اعتماد هذه الوثيقة، تبدأ المرحلة التالية ببناء Backend وقاعدة البيانات المشتركة. لا يبدأ التنفيذ من توسيع Trello، ولا من إضافة صلاحيات واجهة فقط، ولا من اختيار مزود خدمة يخالف القرار المعتمد.
